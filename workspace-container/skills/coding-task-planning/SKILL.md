# 1. Purpose
The `coding-task-planning` skill is a critical bridge between design and execution. It translates a high-level Technical Specification (generated by the `requirement-analysis` skill) into a granular, step-by-step Execution Checklist. By organizing tasks into a Directed Acyclic Graph (DAG), it ensures that all dependencies are fulfilled before they are needed, minimizing blocked states and rework.

# 2. Trigger Conditions
This skill should be invoked under the following circumstances:
- **Initial Planning:** Immediately after the successful completion of the `requirement-analysis` skill and user approval of the Technical Specification.
- **Plan Revision:** 
  - When the user requests a change in direction or scope.
  - When a step becomes blocked due to unforeseen technical constraints.
  - After a significant refactoring decision during the `code-review` phase.

# 3. Step Granularity Rules
The success of the implementation phase depends heavily on the granularity of the planned steps.
- **The "One File" Rule:** A single step should ideally represent the creation or modification of a single file (or a tightly coupled pair, like `Button.tsx` and `Button.css`).
- **Logical Units:** If modifying a single file involves massive changes (e.g., adding 300 lines to a monolithic component), break it down by logical unit:
  - *Step A:* Add state management hooks.
  - *Step B:* Implement event handlers.
  - *Step C:* Wire up the JSX rendering.
- **Testable Milestones:** Group steps so that every 2-3 steps result in a functional, testable milestone. Never go more than 5 steps without having a runnable piece of code that can be verified.

# 4. Dependency Ordering (The DAG Approach)
Tasks MUST be ordered strictly bottom-up. You must never plan to build a consuming component before its children or data dependencies are planned. 

Follow this strict hierarchical ordering:

| Phase | Category | Description | Example Target |
|---|---|---|---|
| 1 | Configuration | Env vars, build configs, package additions. | `tailwind.config.ts`, `package.json` |
| 2 | Types / Interfaces | Data models, API response shapes, prop types. | `src/types/user.d.ts` |
| 3 | Utilities / Helpers | Pure functions, formatters, validators. | `src/utils/formatDate.ts` |
| 4 | State / Store | Global state setup (Zustand, Redux). | `src/store/userStore.ts` |
| 5 | Hooks | Custom React hooks for data fetching/logic. | `src/hooks/useUser.ts` |
| 6 | Presentational UI | "Dumb" components with hardcoded data. | `src/components/ui/Button.tsx` |
| 7 | Container UI | "Smart" components wiring hooks to UI. | `src/components/UserProfile.tsx` |
| 8 | Pages / Routes | Final assembly of components into a view. | `src/app/profile/page.tsx` |
| 9 | Tests | Unit and integration tests. | `src/components/Button.test.tsx` |

# 5. Handling JavaScript Projects
The `/workspace` may contain legacy or pure JavaScript projects where TypeScript is not available.
- **Skip Phase 2 (Types):** Do not plan TypeScript interfaces.
- **Substitute with JSDoc/Schemas:** Instead of defining types, allocate Phase 2 steps to defining standard object shapes using JSDoc comments or runtime validation schemas (like Zod or Joi).
- **Focus on Default Props:** Explicitly plan steps to define `defaultProps` and `propTypes` (if used) in presentational components to maintain clear contracts.

# 6. Incremental Planning for Large Features
For features requiring more than 10 file changes, avoid massive upfront planning. Use an incremental approach:
- **Phase-Based Milestones:** Divide the feature into high-level phases (e.g., "Phase 1: Basic List View", "Phase 2: Filtering and Sorting", "Phase 3: Detail Modal").
- **Just-In-Time (JIT) Detail Planning:** Generate the granular, file-level Execution Checklist ONLY for Phase 1. 
- Leave Phase 2 and Phase 3 as single, high-level placeholder tasks. 
- Expand Phase 2 into granular steps only after Phase 1 is completely implemented and verified.

# 7. Plan Format and Status Tracking
The plan must be maintained as a markdown checklist. The agent is responsible for updating the status indicators as work progresses.

**Status Indicators:**
- `[ ]` Planned (Pending)
- `[-]` In Progress (Currently being worked on)
- `[x]` Done (Implemented and verified)
- `[!]` Blocked (Cannot proceed)

**Example Artifact Format:**
```markdown
### Execution Checklist: Authentication Flow

**Phase 1: Shared UI & Types**
- [x] 1. (Types) Create `AuthResponse` and `User` interfaces in `src/types/auth.ts`.
- [x] 2. (UI) Build `InputField` component in `src/components/InputField.tsx`.
- [-] 3. (UI) Build `SubmitButton` component in `src/components/SubmitButton.tsx`.

**Phase 2: Hooks & Logic**
- [ ] 4. (Hooks) Implement `useLogin` mutation hook in `src/hooks/useLogin.ts`.
- [ ] 5. (Hooks) Implement `useAuthStore` (Zustand) in `src/store/authStore.ts`.

**Phase 3: Assembly**
- [ ] 6. (Container) Build `LoginForm` combining UI and Hooks in `src/components/LoginForm.tsx`.
- [ ] 7. (Page) Create login route in `src/app/login/page.tsx`.
```

# 8. Plan Revision Protocol
Plans are not static. Re-planning is mandatory when encountering roadblocks.

**When to Revise:**
- A required API endpoint is discovered to be missing or differently structured.
- A library incompatibility is found during implementation.
- The `debugging` skill has exhausted its options on a specific step.

**How to Revise:**
1. Halt execution.
2. Mark the failing/blocked step as `[!] Blocked`.
3. Document the specific technical reason for the blockage.
4. Generate a revised plan. This may involve adding new steps (e.g., "Implement polyfill") or changing the approach entirely.
5. Present the revised plan to the user for awareness before continuing.

# 9. Validation Gate
Before moving to implementation, the agent must perform a self-check:
1. **Completeness:** Does this checklist cover 100% of the acceptance criteria in the Technical Specification?
2. **Dependency Check:** Is any component scheduled to be built before its dependencies (hooks, types, sub-components) are completed?
3. **Scope Check:** Are there any "Monolithic Steps" that need to be broken down?

# 10. Anti-patterns
Avoid these common planning failures:
- ❌ **Over-planning:** Creating a 50-step checklist for a large feature upfront. It will inevitably become obsolete as implementation reveals new details. Use Incremental Planning instead.
- ❌ **Top-Down Ordering:** Planning the Next.js `page.tsx` first, then planning the components it needs. This leads to broken builds and mock data sprawl.
- ❌ **Monolithic Steps:** "Step 1: Build the Dashboard". This provides zero guidance. Break it down into layout, widgets, data fetching, etc.
- ❌ **Orphaned State:** Modifying a checklist but failing to communicate the updated status to the user or parent agent.

# 11. Handoff to Implementation
Once the plan is validated:
1. Save the Execution Checklist (preferably as an artifact or in a dedicated scratch file).
2. Transition execution to the `implementation` skill.
3. Feed the `implementation` skill one step at a time, starting with the first `[ ] Planned` task.
4. Require the `implementation` skill to report back upon completion before updating the checklist to `[x] Done` and proceeding.
